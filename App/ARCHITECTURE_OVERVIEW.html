Hakim — Architecture & Codebase Overview

A from-scratch technical map of the Flutter client, built by reading the actual source tree — ~50,800 lines across 90 files. Nothing here is inferred from naming conventions alone; where the codebase doesn't answer a question, that's stated rather than guessed.

Doctor Assistant Admin Core / shared

1 · High-Level Project Overview

Hakim ("physician" in Arabic) is a bilingual (English/Arabic, full RTL) clinic-management mobile app for small private practices. It is a client for a FastAPI-style REST backend (backend.hakim-app.cloud) plus a second, separate AI microservice (ai-api.hakim-app.cloud) referenced in config but — as far as this codebase shows — not called directly; voice transcription and imaging analysis go through the main backend, which presumably proxies to the AI service server-side.

Main features

Patient registry · appointment scheduling with types/statuses · a 6-tab Consultation workflow per visit (Vitals → Patient History → Voice-to-report AI → AI Medical Imaging → Lab Reports → Manual Report) · AI-assisted reporting (voice→transcript→structured report; image→AI draft→doctor review) · report finalization (draft → reviewed → finalized, triggering server-side PDF + WhatsApp delivery) · lab-report PDF upload/viewing · finance/revenue dashboard · admin console (stats, user activation, audit log) · settings (fees, linked assistants, CSV export, language, dark mode) · self-service registration gated behind admin activation.

User roles

Doctor
  • Owns a clinic
  • Full patient / appointment / consultation / finance access
  • Shell: Dashboard, Appointments, Patients, Finance
Assistant
  • Linked to exactly one doctor (doctor_id)
  • Manages that doctor's front-desk workload
  • Shell: Dashboard, Appointments, Patients, Payments
Admin
  • Cross-clinic oversight
  • No clinical data entry
  • Shell: Dashboard, Users, Patients, Audit Logs

Overall architecture

A pragmatic two-layer MVVM — not a full Clean-Architecture stack. There is no repository layer, no use-case classes, and almost no domain entity classes. ApiService methods return raw Map<String,dynamic>/List<dynamic> straight from Dio, and ViewModels store those same raw maps in state. The only real model classes are UserProfile, AppError, RegistrationData, and three small classes living inside admin_viewmodel.dart (AdminStats, AdminUser, AuditLog). Know this before hunting for a Patient or Appointment class — there isn't one; see §9.

State management is Riverpod (StateNotifierProvider), theming is per-role (three ThemeExtensions), navigation is plain Navigator.push/MaterialPageRoute — no named-route table, no router package.

4 · Entry Point

main.dart → main():

  1. ApiService.init()Constructs the single Dio instance — base URL, timeouts, the X-API-KEY + Bearer request interceptor, response/error logging, global 401 handling.
  2. registerUnauthorizedHandler(...)Wires a callback that resets AuthViewModel's static instance and force-navigates to LoginPage on any 401, anywhere.
  3. runApp(ProviderScope(child: MyApp()))MyApp watches themeModeProvider + localeProvider; home is _StartupRouter.
  4. _StartupRouter shows SplashScreenThen calls _resolveInitialScreen() in initState.
  5. Read token / role / profileFrom secure storage. Missing or JWT exp already passed (decoded client-side, no crypto lib) → LoginPage.
  6. Rebuild UserProfile from cacheIncluding doctorId/doctorEmail for assistants — skips the expensive discovery lookup on warm restarts.
  7. Read last-active tabFrom SettingsService — default tab 1 (Appointments) for assistants, tab 0 otherwise.
  8. pushReplacement to the role shellPre-seeded with profile + tab index; 300ms fade. Splash is never seen again this process lifetime.

No manual setState round-trip is needed — Riverpod's ref.watch triggers a rebuild whenever copyWith produces a new state object.

The one workflow worth tracing end-to-end: consultation completion

  1. Resolve the active visitensureVisitExists()
  2. If a voice/manual report exists in DRAFT/REVIEWEDDoctorViewModel.finalizeReport(reportId) — promotes DRAFT→REVIEWED first if needed, then POST .../finalize (120s timeout; backend generates PDF + sends WhatsApp, fire-and-forget on its side — report is FINALIZED even if WhatsApp fails)
  3. Submit staged AI-imaging confirmationsreviewMedicalImage(imageId, diff) once per image
  4. Mark visit COMPLETEDupdateVisitStatus
  5. Mark appointment COMPLETEDupdateAppointmentStatus
  6. Refresh appointment listfetchAppointments()
Imaging-only consultations (no voice/manual report) skip step 2 entirely — there is no "anchor" empty report created for them; a follow-up fix removed that behavior because it caused a duplicate WhatsApp send.

7 · State Management

  • Solution: flutter_riverpod ^2.5.1 — StateNotifierProvider + StateNotifier<T> for every stateful feature, plus a couple of plain StateProviders and one hand-rolled notifier for locale.
  • Initialization: a single ProviderScope wraps the app in main(). No provider overrides anywhere (no test/mock wiring present).
  • Managing classes: AuthViewModel, DoctorViewModel, AssistantViewModel, AdminViewModel, SettingsViewModel, LocaleNotifier — each paired with an immutable *State + copyWith.
  • UI updates: views are ConsumerWidget/ConsumerStatefulWidget; ref.watch rebuilds, ref.read(...).method() triggers actions, ref.listen runs one-shot side effects like post-login navigation.
  • No autoDispose: called out explicitly in three of the four provider files' own comments — state survives navigation so cached IDs/lookups aren't repeated, at the cost of needing manual invalidation on logout (authLogoutCleanupProvider).
  • Local-only UI state (tab index, form controllers, animations) stays as plain State/setState — not lifted into Riverpod.

8 · API Layer

  • Single gateway: lib/services/API_Service.dart — one static Dio instance, ~60 endpoint methods. Exception: auth_viewmodel.dart uses the raw http package (not _dio) for the two self-registration endpoints — those calls bypass the shared interceptor entirely, so they get no standardized error-detail extraction and no 401 handling.
  • Dio config: base URL from AppConfig.backendBaseUrl (default https://backend.hakim-app.cloud), 30s connect / 60s receive timeout (bumped to 120s just for finalizeReport).
  • Interceptor: onRequest injects X-API-KEY + Bearer token and logs the call; onResponse logs status; onError extracts a readable detail from FastAPI-style bodies and — on 401 — clears stored credentials and fires the app-wide logout callback, guarded against double-firing.
  • Base URL / key location: lib/config/app_config.dart — all four values are String.fromEnvironment with hardcoded fallbacks, meaning the production API key currently ships baked into the client binary as a fallback constant.
  • aiApiBaseUrl: defined but not referenced anywhere else in lib/ — voice/imaging calls go through the main backend. Worth confirming with the backend team whether a direct-to-AI path is planned.
  • Auth flow: POST /auth/login → JWT stored in flutter_secure_storage → role decoded client-side from the payload (base64url-decoded manually, not signature-verified — acceptable here since claims only drive UI routing, never authorization) → profile enriched by cross-referencing /users/doctors//users/assistants by email → persisted for session restore.
  • Token storage: flutter_secure_storage, keys access_token / user_role / user_profile (a JSON blob of the whole profile, so cold start redraws the UI with zero network calls).
  • Error handling: errors/error_handler.dart classifies everything into an AppError with a log-only technical string and a display-ready userMessage.

Everything else — Patient, Appointment, Visit, MedicalReport, MedicalImage, LabReport, Vitals, AppointmentType — is a raw Map<String,dynamic>, never a typed class. This is consistent across every ViewModel and widget (e.g. appointment['patient_first_name']). It's the single biggest thing to internalize before changing this code: there's no compiler-enforced schema for these objects, and field-name mismatches with the backend (several fixed in code comments — e.g. lab-report report_url vs report_file) are a recurring bug source precisely because of this.

10 · Navigation

  • Routing system: none of the router packages — plain Navigator.push(MaterialPageRoute(...)) for drill-in, pushReplacement/pushAndRemoveUntil for full-stack swaps.
  • Initial route: decided imperatively in main.dart's _resolveInitialScreen() — a widget returned by a function, not a named route.
  • Named routes: not used — MaterialApp has no routes:/onGenerateRoute:.
  • Role-based navigation: each role shell owns a hand-built bottom nav (a Row of InkWells, not Flutter's BottomNavigationBar). Selected index is persisted per-role via SettingsService.setLastTab. Switching roles only happens by logging out and back in.
  • Consultation sub-nav: a TabController-driven TabBarView, 6 tabs, NeverScrollableScrollPhysics — reachable only via the TabBar, not swipe.
